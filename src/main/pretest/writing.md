### 대규모 트래픽 설계

- 이벤트로 인한 상품 상세 페이지 대규모 트래픽
- 초당 2,000건 -> 초당 20,000건 (x10)
- LB로 서버 인스턴스 여러대 가용중
- DB MySQL 단일 Primary
  - 단일 DB 부하집중
- Cache: 별도 캐시 시스템 없음
- 상품 상세 정보는 자주 변경되지 않음
- 재고 수량은 주문에 따라 실시간으로 변경됨
  - 별도의 주문 재고차감 API 운영할 것

(현상, 원인, 개선, 트레이드 오프, 장애, 검증)
- DB CPU 95%로 증가
- DB Connection Pool 100%
- API p95 latency 4.5s 증가

1. 현재 상황에서 가장 먼저 의심해야 할 병목 지점을 설명하세요.
- DB에 부하가 집중되고 있기 때문에 슬로우 쿼리(N+1)가 나가고 있지 않은지 확인합니다.
- DB 인스턴스의 스펙이 이벤트 상황을 대비해 작진 않은지 확인합니다.

2. 상품 상세 API의 트래픽을 처리하기 위해 어떤 구조적 개선을 적용할지 설명하세요.
- 상품 조회에 쓰이는 Index가 잘 걸려있나 확인합니다. 그리고 JOIN 테이블들에 쿼리가 N+1 회 나가지 않는지 코드를 확인합니다.
- 그럼에도 해결되지 않는다면 배치를 사용해 Redis 캐시 시스템을 도입합니다.
- '상품 정보는 자주 변경되지 않기' 때문에 재고 수량을 제외한 메타 데이터들을 캐시에 저장해두고 변경이 일어날때만 DB로부터 값을 읽어오도록 합니다.

3. 상품 정보와 재고 정보의 특성이 다르다는 점을 고려하여 캐시 전략을 설명하세요.
- 재고 정보는 실시간성으로 캐시에 적합하지 않기 때문에 DB를 직접 읽어 값을 리턴합니다. 그외에 상품 정보는 캐시에 저장한다음 상품에 변경이 없는 한 TTL 3일을 
유지해 이벤트 상황의 DB 과부하를 줄이겠습니다. 상품 정보에 변경이 있는 경우 즉시 DB에서 값을 읽고 캐시를 갱신합니다.

4. DB 부하를 줄이기 위해 적용할 수 있는 방법을 2가지 이상 설명하세요.
- Read only Replica를 두고 부하를 나누도록 분배합니다. 
- Scale up으로 DB 스펙을 높여 이벤트가 발생할 때에 부하를 받아낼 수 있도록 조치합니다. 다만 평소 상황에서 불필요한 운영 비용이 증가합니다.  

5. 제안한 구조에서 캐시 장애나 DB 장애가 발생했을 때 서비스 영향을 줄이기 위한 방법을 설명하세요.
- Cache 응답에 Timeout을 설정하고 실패할 경우 DB를 읽도록 합니다. 모든 트랜잭션이 DB로 한번에 몰리면 장애가 발생하기 때문에 Timeout을 두고 
즉각적인 장애 조치를 진행합니다.  

6. 개선 작업 후 실제로 효과가 있었는지 판단하기 위해 어떤 지표를 모니터링할지 설명하세요.
- Stage DB 조회 부하 테스트를 진행하면서 그에 따른 DB Connection Pool 감소, 증가 그리고 MySQL CPU를 모니터링 합니다.
